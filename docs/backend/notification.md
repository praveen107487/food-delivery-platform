# Module 11 – Notification

## Overview

The Notification module is responsible for **customer notification management** in the Food Delivery Platform.

It provides customer-facing APIs for:
- Listing customer notifications
- Retrieving specific notification details
- Marking notifications as read
- Marking all notifications as read

This module follows the standard layered architecture using the Repository Pattern, Service Layer, and Dependency Injection. Notifications are generated by business events from other modules and consumed by customer applications.

---

# Responsibilities

The Notification module is responsible for:
- Notification retrieval
- Notification listing with pagination
- Notification filtering (by read status, type)
- Read status management
- Notification ownership validation

The module is **not** responsible for:
- Notification generation (handled by other modules via service calls)
- Real-time notification delivery (deferred to future implementation)
- Push notifications (deferred to future implementation)
- Email/SMS notifications (deferred to future implementation)
- Notification preferences (deferred to future implementation)

## Mark as Read

```text
Client
    │
    ▼
PATCH /notifications/{notification_id}/read
    │
    ▼
NotificationService.mark_as_read()
    │
    ├── Validate Notification Exists
    ├── Validate Ownership
    ├── Check Already Read
    ├── Update Read Status
    ├── Save Changes
    ├── Commit Transaction
    ▼
Return NotificationResponse
```

---

## Mark All as Read

```text
Client
    │
    ▼
PATCH /notifications/read-all
    │
    ▼
NotificationService.mark_all_as_read()
    │
    ├── Batch Update Unread Notifications
    ├── Commit Transaction
    ▼
```

# API Endpoints

## List Notifications

| Method | Endpoint | Authentication |
|----------|----------|----------------|
| GET | `/api/v1/notifications` | Yes |

Lists customer notifications with pagination and filtering.

Query Parameters:
- `page` - Page number (default: 1)
- `page_size` - Items per page (default: 20)
- `is_read` - Filter by read status (optional)
- `type` - Filter by notification type (optional)

---

## Get Notification

| Method | Endpoint | Authentication |
|----------|----------|----------------|
| GET | `/api/v1/notifications/{notification_id}` | Yes |

Returns detailed information for a specific notification.

---

## Mark as Read

| Method | Endpoint | Authentication |
|----------|----------|----------------|
| PATCH | `/api/v1/notifications/{notification_id}/read` | Yes |

Marks a specific notification as read.

---

## Mark All as Read

| Method | Endpoint | Authentication |
|----------|----------|----------------|
| PATCH | `/api/v1/notifications/read-all` | Yes |

Marks all unread notifications as read.

# Business Rules

Implemented business rules:
- Customers can only access their own notifications
- Marking an already read notification is idempotent
- Mark all as read only updates unread notifications
- Notifications are ordered by creation date (newest first)
- Notifications can be filtered by read status
- Notifications can be filtered by type
- Pagination is supported for notification listing

---

# Repository Pattern

Repository responsibilities:
- Read operations
- Write operations
- Persistence only
- Filtering support
- Pagination support
- Batch update operations

Repositories do not:
- Validate business rules
- Verify ownership
- Commit transactions
- Raise HTTP exceptions

The service layer owns:

# Design Decisions

## Batch Update for Mark All Read

Uses bulk SQL update instead of individual updates because:
- More efficient for multiple notifications
- Reduces database round trips
- Better performance for customers with many notifications
- Single transaction for consistency

---

## Idempotent Mark as Read

Already read notifications return without changes because:
- Prevents unnecessary database writes
- Simplifies client logic
- Improves performance
- Standard REST practice

---

## Filtering at Repository Level

Filters applied in repository queries because:
- Reduces data transfer
- Improves query performance
- Leverages database indexing
- Keeps service layer focused on business logic

---

## Customer Ownership Validation

Service validates ownership because:
- Security requirement
- Prevents unauthorized access
- Centralized business rule
- Consistent with other modules
